DAG Reference

Understanding SCUD's dependency graph and how Descartes computes execution waves.

Overview

Descartes uses SCUD's DAG (Directed Acyclic Graph) for task dependency management. Tasks are organized into waves - groups of tasks that can execute in parallel because their dependencies are satisfied.

Wave 1: [A] [B] [C] ← No dependencies │ │ │ └───────┼───────┘ │ Wave 2: [D] ← Depends on A, B, C │ Wave 3: [E] ← Depends on D

How Waves are Computed

Descartes uses Kahn's algorithm for topological sorting:

  1. Load tasks from SCUD storage
  2. Filter to actionable tasks (Pending status, not expanded)
  3. Identify start nodes (tasks with no unsatisfied dependencies)
  4. Group into waves (tasks become ready when all dependencies complete)
  5. Execute sequentially by wave, tasks within a wave can run in parallel

Example

# View waves for a tag
scud waves --tag my-feature

# Or via Descartes
descartes waves
Wave 1 (2 tasks): [1] Setup project structure [2] Configure database connection Wave 2 (2 tasks): [3] Create User model (depends: 2) [4] Create API routes (depends: 1) Wave 3 (1 task): [5] Add authentication (depends: 3, 4)

# Via SCUD CLI

# Via PRD (implicit from structure)
# Tasks are numbered in order, dependencies inferred

Dependency Rules

RuleDescription
No cyclesA task cannot depend on itself or create circular dependencies
TransitiveIf A depends on B, and B depends on C, then A implicitly depends on C
External depsDependencies on tasks outside the current tag are ignored
Done depsDependencies on completed tasks are considered satisfied

Validating Dependencies

# Check for issues
scud check-deps --tag my-feature

# Auto-fix common issues
scud check-deps --fix --tag my-feature

Wave Execution

Execution Order

  1. Compute waves from DAG
  2. Execute Wave 1 (all tasks in parallel rounds)
  3. Run validation after Wave 1 completes
  4. If validation passes, execute Wave 2
  5. Repeat until all waves complete

Round Size

Within each wave, tasks are executed in "rounds" to manage parallelism:

# Default: 5 tasks per round
descartes ralph --scud-tag feature

# Custom round size (for rate limiting)
descartes ralph --scud-tag feature --round-size 3

Task Status Flow

┌─────────┐ │ Pending │ └────┬────┘ │ wave ready ┌────▼────┐ │InProgress│ └────┬────┘ ┌─────────────┼─────────────┐ │ │ │ ┌─────▼────┐ ┌─────▼────┐ ┌─────▼────┐ │ Done │ │ Failed │ │ Blocked │ └──────────┘ └──────────┘ └──────────┘
StatusDescription
PendingTask waiting for dependencies or wave execution
InProgressAgent currently working on task
DoneTask completed successfully
FailedTask or validation failed (will retry)
BlockedAgent reported TASK_BLOCKED (external dependency)

Backpressure Validation

Validation runs after each wave to catch issues early:

# Single command
descartes ralph --scud-tag feature --verify "cargo test"

# Multiple commands
descartes ralph --scud-tag feature --verify "cargo test && cargo clippy"

On Validation Failure

  1. All tasks in the current round are marked Failed
  2. Descartes retries failed tasks (up to 3 attempts)
  3. Failed task context includes validation output
  4. Fresh agent spawned for each retry

SCUD Storage Format

Tasks are stored in .scud/tasks/tasks.scg using SCUD's token-efficient format:

# Example SCG format
[task:1]
title: Setup project structure
status: done
deps: []
desc: Create initial directory layout

[task:2]
title: Configure database
status: pending
deps: []
desc: Set up PostgreSQL connection

[task:3]
title: Create User model
status: pending
deps: [2]
desc: Add User entity with fields

Integration with Descartes

Fresh Context Per Task

Each task in a wave gets:

  • A completely fresh agent session
  • Task details from SCUD (ID, title, description, dependencies)
  • Optional plan/spec context
  • No history from previous tasks
Why Fresh Context? The Ralph Wiggum loop pattern ensures each task starts clean. This prevents:
  • Context drift from accumulated state
  • Cross-contamination between tasks
  • Non-deterministic behavior from prior context

Context Handoff

For long-running tasks that exceed context limits (60% of window), Descartes performs a handoff:

  1. Summarize current agent's progress
  2. Close current session
  3. Spawn new agent with original spec + summary
  4. Continue task execution
